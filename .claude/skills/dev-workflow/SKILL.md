# 개발 워크플로우 실행 절차

규칙 원문은 `CLAUDE.md`, 모델 배분은 `.claude/rules/model-allocation.md`다. 이 스킬은 그 둘을 "누가, 언제" 하는지로 옮긴 것이다.
사람 승인이 필요한 곳(🔒)에서는 반드시 멈추고 답을 기다린다. 승인은 사람이 채팅으로 한 말만 인정한다.

| 단계 | 담당 에이전트 (모델 수준) | 끝나는 조건 |
|---|---|---|
| 1. 요구사항·케이스 분석 | `case-analyst` (좋은 모델) | 🔒 사람이 케이스 목록 승인 |
| 2. 테스트 작성 | `test-writer` (좋은 모델) | 새 테스트가 실패(Red)함을 실행으로 확인 |
| 2-1. 테스트 리뷰 | `test-reviewer` (좋은 모델) | 판정 `통과` + 🔒 사람이 테스트 승인 |
| 3. 구현 | `implementer` (저렴한 모델) 또는 `implementer-hard` (좋은 모델) | 전체 테스트 통과(Green) + 정리 후 재통과 |
| 6. 검증 | 직접 실행 + 실패 시 `failure-analyst` (좋은 모델) | 단위·회귀·통합 테스트 전부 통과 |
| 7. 완료 보고 | 직접 | 보고서 제출 |

## 1. 케이스 분석
- `case-analyst`에게 요구사항 원문 전체와 관련 파일 경로를 넘긴다.
- 돌아온 케이스 목록과 "확인 필요" 목록을 사람에게 그대로 보여준다.
- 🔒 승인을 받는다. 사람이 빼거나 고친 케이스는 이유와 함께 케이스 목록에 기록한다.

## 2. 테스트 작성
- 승인된 목록만 `test-writer`에게 넘긴다.
- Red가 아닌 테스트가 있으면 원인을 사람에게 보고한다.
- `test-reviewer`로 점검한다. `수정 필요`면 `test-writer`가 고치고 다시 점검한다.
- 🔒 사람에게 테스트 코드 승인을 받는다.

## 3. 구현 — 담당 고르기
- 동시성(동시 요청·락·조건부 UPDATE), 복잡한 상태 관리, 레거시 수정이 들어가면 처음부터 `implementer-hard`.
- 그 외는 `implementer`.
- 구현 담당이 "테스트가 잘못됐다" 또는 "확인 필요"를 보고하면 멈추고 사람에게 올린다(CLAUDE.md 4·5단계).

## 실패했을 때 (에스컬레이션)
1. 실패 출력을 `failure-analyst`에게 넘겨 분류를 받는다.
2. 분류별 조치:
   - **구현 버그** → 같은 구현 담당이 다시 시도. 같은 작업이 `implementer`에서 2~3회 연속 실패하면 `implementer-hard`로 올리고 `.claude/notes/escalation-log.md`에 기록한다.
   - **테스트 오류** → 2단계로 되돌린다. 🔒 사람 승인 후 `test-writer`가 고친다. 테스트 변경은 구현 변경과 다른 커밋으로 남긴다.
   - **불안정한 테스트** → 원인을 사람에게 보고한다. skip 처리하지 않는다.
   - `implementer-hard`에서도 같은 작업이 3회 실패하면 → 멈추고 설계 문제로 사람에게 보고한다(4번째 수정 금지).

## 6. 검증
- `./gradlew test` 로 단위·회귀 테스트, 통합 테스트까지 전부 돌린다. 커버리지 숫자만 보고 끝내지 않는다.
- **증거 없이 "완료·통과"라고 말하지 않는다.** 이번에 직접 실행한 명령의 출력(실패 0건, 종료 코드 0)을 보고 나서만 말한다. 예전 실행 결과나 "통과할 것"은 증거가 아니다.
- 에이전트가 "성공"이라고 보고해도 그대로 믿지 않는다. `git diff`로 실제 바뀐 파일을 보고 테스트를 다시 돌려 확인한다.
- 버그 수정 회귀 테스트는 한 번 확인한다: 수정을 잠시 되돌리면 테스트가 실패하고, 다시 넣으면 통과하는지.

## 리뷰 의견을 받았을 때 (CodeRabbit·팀원)
- 반영하기 전에 이 코드베이스에서 실제로 맞는지 확인한다(호출되는 곳이 있는지, 기존 동작을 깨는지, 지금 구현의 이유가 있는지).
- 의견 중 하나라도 이해가 안 되면 아무것도 고치지 말고 먼저 묻는다 — 항목끼리 이어져 있을 수 있다.
- 틀렸다고 보면 근거를 대고 반대 의견을 낸다. 쓰이지 않는 기능을 "제대로" 만들자는 의견에는 정말 필요한지 먼저 묻는다.
- 반영은 한 항목씩, 항목마다 테스트를 돌린다. 순서: 깨짐·보안 → 간단한 수정 → 복잡한 수정.
- 리뷰 의견이 테스트를 바꾸라는 내용이면 CLAUDE.md 4단계(사람 승인)를 따른다.
