# 작업별 모델 배분 기준

## 원칙
- 잘못되면 뒤 단계 전체가 틀어지는 작업에는 **좋은 모델**을 씁니다.
- 테스트로 검증 가능한 구현 작업은 **저렴한 모델**을 씁니다. 구현은 토큰 사용량이 가장 많아서 비용 절감 효과가 가장 큽니다.
- 저렴한 모델이 같은 작업에서 반복 실패하면 **상위 모델로 올립니다.**
- 모델 성능과 가격은 자주 바뀌므로, 특정 모델명보다 **작업 유형 기준**으로 관리합니다.

## 작업별 배분

| 작업 | 모델 수준 | 이유 |
|---|---|---|
| 케이스·예외 케이스 도출 | 좋은 모델 | 넓이와 누락 방지가 중요 |
| 요구사항 분석, 설계 | 좋은 모델 | 잘못되면 전체가 틀어짐 |
| 시나리오 정의 | 좋은 모델 | 사람 승인 전 단계의 품질을 결정 |
| 테스트 코드 작성 | 좋은 모델 | 명세 역할을 하므로 품질이 중요 |
| 테스트 리뷰, 테스트 품질 점검 | 좋은 모델 | 판단 품질이 핵심 |
| 실패 원인 분석 (구현 버그 / 테스트 오류 / 불안정 테스트) | 좋은 모델 | 흐름 전체의 품질을 좌우 |
| 일반 구현 | 저렴한 모델 | 테스트로 검증 가능, 비용 비중이 큼 |
| 어려운 구현 (동시성, 복잡한 상태 관리, 레거시 수정) | 처음부터 좋은 모델 | 저렴한 모델의 실패 비용이 큼 |
| 반복 실패한 구현 | 상위 모델로 에스컬레이션 | 같은 작업에서 2~3회 실패 시 올림 |

## 에스컬레이션 규칙
- 같은 구현 작업이 **2~3회 연속 실패**하면 상위 모델로 올립니다.
- 실패 원인이 테스트 오류로 판명되면, 구현 모델이 아니라 **테스트 작성 단계로 되돌려** 좋은 모델이 수정하게 합니다.
- 올린 기록(작업, 실패 횟수, 원인)을 남겨 두면 나중에 배분 기준을 조정할 수 있습니다.

## 검증 방법
- 같은 구현 작업을 여러 모델에 맡겨 보고 **테스트 통과율, 재작업 횟수, 비용**을 비교합니다.
- 분기마다 한 번씩 이 기준을 점검합니다.

## 담당
- 배분 기준 관리: 개발 리드
- 테스트 승인: 개발자
- 시나리오 승인: 기획 또는 QA
