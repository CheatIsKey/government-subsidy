# TDD 기록

이 프로젝트는 기능마다 **케이스 분석 → 사람 승인 → 테스트 먼저(Red) → 구현(Green) → 리팩터링 → 검증** 순서로 만든다(규칙: [`CLAUDE.md`](../../CLAUDE.md)).
이 폴더는 작업마다 "무엇을 정했고, 테스트가 어떤 버그를 잡으며, 리뷰에서 무엇을 배웠는지"를 남긴다.

| 번호 | 작업 | 상태 |
|---|---|---|
| [01](01-sync-list-collection.md) | 공공 API 목록 수집·정리·실행 기록 (SYNC-1, 5, 9) | 완료 (PR #3) |
| [02](02-service-key-masking.md) | 서비스 키 노출 방어 (이슈 #4, OPS-5) | 완료 (PR #8) |

## 기록 한 편의 구성

| 칸 | 내용 |
|---|---|
| 목표 | 무엇을 만들었나 |
| 흐름 | 단계별로 언제 무엇을 했나 |
| 케이스와 결정 | 어떤 상황을 다루기로 했고, 왜 그렇게 정했나 |
| 테스트가 잡는 버그 | "이렇게 잘못 만들면 이 테스트가 실패한다" |
| 리뷰에서 배운 것 | 문제 → 원인(개념) → 고친 방법 |
| 결과 | 테스트 수, 커밋, PR |

## 지금까지 배운 TDD 원칙

| 원칙 | 한 줄 | 처음 나온 곳 |
|---|---|---|
| Red는 "올바른 이유"로 실패해야 한다 | "구현 안 됨" 예외로 실패하는 것만으로는 단언이 버그를 잡는지 알 수 없다. 껍데기가 빈 값을 돌려줄 때도 **단언에서** 실패하는지 확인한다 | 01 |
| 통과가 정상인 짝 테스트가 있다 | "2,000건 허용"처럼 기대가 "아무것도 안 함"과 같은 테스트는 지금 통과한다. 너무 엄격하게 잘못 만든 구현을 잡는다 | 01 |
| 조건을 바꿔 결과가 바뀌는지 짝으로 본다 | 테스트 하나로는 "그 조건 때문에" 일어났는지 증명할 수 없다 | 02 |
| 흔들리는 테스트가 가장 해롭다 | 시계·시간대·타임아웃·순서에 기대면 통과했다 실패했다 한다. 고정 시계, UTC, 넉넉한 시간, 짝 테스트로 막는다 | 01, 02 |
| 확인하려는 것에 가장 가까운 곳에서 확인한다 | 로그는 콘솔 글자가 아니라 로거에서 센다 | 02 |
| 테스트가 시험하는 상황이 케이스와 같은지 실제 실패 메시지로 확인한다 | "본문 잘림"을 재현하려다 HTTP/2 오류를 재현하고 있었다 | 02 |
| 기존 테스트 변경은 따로 승인받고 따로 커밋한다 | 테스트를 약하게 만들어 통과시키는 것을 막는다 | 01 |
| 재현이 어려운 상황은 판단 코드만 떼어 단위 테스트로 지킨다 | 연결 대기 시간 초과는 예외 객체만 만들어 분류 함수를 시험한다 | 02 |
| 라이브러리가 일하는 순서와 예외 집안을 소스로 확인한다 | `retrieve()`는 상태 확인보다 Content-Type 해석이 먼저라, 우리 catch를 건너뛰는 예외가 있었다 | 02 |
| 리뷰 지적은 새 케이스로 받아 같은 절차를 다시 탄다 | 케이스 추가 → 승인 → Red → Green. 채택하지 않는 지적은 근거를 답글로 남긴다 | 02 |
| 검사하는 코드는 검사받는 쪽이 고칠 수 없는 곳에서 실행한다 | PR 리뷰 판정 스크립트는 PR 쪽이 아니라 기준 브랜치(dev) 원본으로 돌린다. PR이 검사를 `exit 0`으로 고쳐 자기 자신을 통과시키지 못하게 | PR #11 |
