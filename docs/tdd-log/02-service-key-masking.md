## 무엇이 진짜 문제였나

```
500 Internal Server Error: "<html><body>Internal Error ab+c/d==</body></html>"
```

`ab+c/d==`가 테스트용 가짜 키다. 공공 API 오류 페이지가 요청 주소를 그대로 되돌려 주면, 진짜 키가 이렇게 예외 메시지에 들어간다.
비유하면 **반송 봉투의 주소는 가렸는데, 상대가 편지 안에 내 비밀번호를 적어 돌려보낸 경우**다.

**배운 점:** 이슈의 전제는 소스와 실제 실행으로 확인한 뒤에 적는다. 이번에는 "URL로 샌다"는 전제는 틀렸지만, 테스트를 써 보니 "본문으로 샌다"는 진짜 경로가 나왔다.

## 케이스와 결정

| 결정 | 이유 |
|---|---|
| 실패는 우리 예외 `Gov24ApiException`으로 감싼다. 메시지는 종류·HTTP 상태·경로·page·공공 API `code`만 | 라이브러리가 바뀌어도 메시지 형식이 안전하게 유지되고, 재시도(#6)가 기댈 예외 종류가 생긴다 |
| 원래 예외는 안에 넣지 않고 클래스 이름만 | 넣으면 로그의 "Caused by" 줄에 원래 메시지와 본문이 그대로 나온다 |
| 응답 본문은 넣지 않고 공공 API `code`만 (예: `code=-4`) | 원인 파악에는 code로 충분하고, HTML 오류 페이지에는 무엇이 들어 있을지 모른다 |
| 외부에서 온 글은 키 네 형태를 `****`로 가린다 | 원래 값 `ab+c/d==`, 대문자 인코딩 `ab%2Bc%2Fd%3D%3D`, 소문자 인코딩, 부분 인코딩 `ab%2Bc/d==` |
| `Gov24Client`는 로그를 남기지 않는다 | 같은 실패가 여러 번 찍히지 않게. 로그는 실패를 처리하는 쪽이 남긴다 |
| HTTP/1.1 고정 | 아래 리뷰 1번 |
| 연결을 맺지 못함 = CONNECTION, 맺은 뒤 문제 = IO | 아래 리뷰 2번 |
| 메시지 형식 `<종류> status= path= page= code= cause=<전체 클래스명>`, 값 없는 칸은 뺌 | 예: `HTTP_ERROR status=401 path=/api/gov24/v3/serviceList page=3 code=-4` |
| 상태 코드를 먼저 읽는다 (`retrieve()` 대신 `exchange()`) | 아래 리뷰 7번. Content-Type 해석보다 상태 확인이 먼저 와야 한다 |
| 4xx/5xx에서 본문을 읽다 실패하면 상태를 붙이고, 종류는 기존 분류 규칙을 따른다 (보통 IO) | 아래 리뷰 8번 |

| 200인데 Content-Type을 해석할 수 없음 = 성공으로 보지 않고 IO(상태 200) | 무엇이 왔는지 모르는 응답으로 혜택 데이터를 만들지 않는다. 헤더 값은 메시지에 넣지 않는다 |

## 리뷰에서 배운 것

### 1. 테스트가 시험하는 상황이 케이스와 달랐다 (E7)

- **상황:** "응답 본문이 중간에 깨지면 IO로 감싸는지" 시험하려고 가짜 서버에 깨진 본문을 보내게 했다.
- **실제:** `protocol error: Frame type(100) length(7107435) exceeds MAX_FRAME_SIZE(16384)` — 본문 잘림이 아니라 HTTP/2 형식 오류였다.
- **원인 (개념):**
  - 자바 HTTP 클라이언트의 기본값은 **HTTP/2**라서 `http://`에도 "HTTP/2로 바꿀까?"를 먼저 묻는다(업그레이드).
  - 가짜 서버가 받아들인 뒤 깨진 **글자**를 보내자, 클라이언트는 그걸 HTTP/2 **프레임 머리**(길이·종류가 적힌 앞부분)로 읽었다. 글자가 "길이" 자리에 들어가 700만이라는 값이 나왔다.
  - 비유: "이제 숫자로 대화하자"고 약속한 직후 상대가 영어 단어를 보낸 상황.
- **고친 방법:** 클라이언트를 HTTP/1.1로 고정하고, "본문 1,000바이트"라고 알린 뒤 10바이트만 보내고 끊어서 진짜 잘림을 재현한다.
- **고친 뒤 실제 실패 메시지:** `fixed content-length: 1000, bytes received: 9` → `EOFException`. WireMock은 Content-Length를 실제 길이로 알아서 고쳐서 이 상황을 못 만들어, 작은 HTTP/1.1 서버(`TruncatedBodyServer`)를 직접 만들었다.
- **원칙:** 테스트가 실패할 때 **실제 실패 메시지**를 읽고, 그게 케이스가 말하는 상황인지 확인한다. 도구가 "친절하게" 고쳐주는 바람에 원하는 고장을 못 만드는 경우도 있다.

### 2. 예외 종류로 나눌 수 없는 것을 종류로 나누려 했다 (E6)

- **상황:** "연결 실패"와 "연결 끊김"을 둘 다 CONNECTION으로 분류하기로 했었다.
- **원인 (개념):**

  | 경우 | 단계 | 자바가 주는 예외 |
  |---|---|---|
  | 포트 닫힘 | 연결을 맺기 **전** (TCP 핸드셰이크에서 거절) | 항상 `ConnectException` |
  | 연결 끊김 (reset) | 연결을 맺고 요청을 보낸 **뒤** | 일반 `IOException`, EOF 등 그때그때 다름 |

  - 비유: "없는 번호입니다"는 늘 같은 안내지만, 통화 중 끊김은 끊기는 순간마다 다르게 들린다.
  - WireMock의 연결 끊김 재현은 Windows에서 멈출 수 있다고 문서에 적혀 있다.
- **고친 방법:** 기준을 "연결을 맺었는가"로 바꿨다. 맺지 못함(포트 닫힘, 연결 대기 시간 초과) = CONNECTION, 맺은 뒤 문제 = IO. 연결 대기 시간 초과는 자바에서 "시간 초과" 예외의 한 종류라 TIMEOUT보다 **먼저** 검사한다.
- **잃는 것:** 없다. 재시도(#6)에서 둘 다 다시 시도할 대상이다.

### 3. 몸 풀기 첫 바퀴에도 기록 제한을 걸었다 (타임아웃)

- **상황:** 0.3초 타임아웃 클라이언트를 정상 응답 테스트에도 썼다.
- **실제:** 이 PC에서도 첫 호출이 0.46초 걸렸다(연결 준비, 클래스 로딩, JIT). GitHub의 CI 서버는 더 느릴 수 있다.
- **원칙:** 코드가 맞는데 통과했다 실패했다 하는 **흔들리는 테스트(flaky)**는 진짜 실패를 무시하게 만든다.
- **고친 방법:** 정상 테스트는 5초, 짧은 제한은 타임아웃 시험에만. 지연은 제한의 몇 배로.

### 4. 설정을 무시한 구현도 통과했다 (E5)

- **상황:** 지연 3초, 설정 0.3초로 "TIMEOUT이 나는지"만 봤다. 설정을 무시하고 1초를 박아 넣어도 3초 전에 끊기니 통과한다.
- **리뷰 제안의 한계:** "2초 안에 끝났나"를 더해도, 1초 고정 구현은 2초 안에 끝나서 여전히 통과한다.
- **고친 방법 (짝 테스트):** 같은 지연(1.5초)에 설정만 바꿔 두 번.

  | 엉터리 구현 | 짧은 설정(0.3초) → TIMEOUT 기대 | 긴 설정(5초) → 정상 기대 |
  |---|---|---|
  | 1초 고정 | 통과 | **실패** |
  | 10초 고정 | **실패** | 통과 |
  | 타임아웃 없음 | **실패** | 통과 |
  | 설정대로 | 통과 | 통과 |

- **원칙:** "A면 B"를 하나만 보면 B가 다른 이유로 일어나도 통과한다. **조건을 바꾸면 결과도 바뀌는지** 짝으로 본다.
- connect-timeout은 "응답 없는 IP" 재현이 네트워크마다 달라서 이번에는 시험하지 않는다(범위 밖에 기록).

### 5. 로그를 콘솔 글자 모양으로 확인했다 (E11)

- **상황:** "Gov24Client는 로그를 남기지 않음"을 콘솔에서 `Gov24Client  :` 글자를 찾아 확인했다.
- **놓치는 경우:** 로그 형식이 JSON으로 바뀜 / 다른 로거 이름 / DEBUG 로그(기본 INFO라 콘솔에 안 나옴. 운영에서 DEBUG를 켜면 그때 샌다).
- **개념:** 로거(로그 창구), 레벨(TRACE < DEBUG < INFO < WARN < ERROR), 어펜더(로그를 보낼 곳). `ListAppender`는 로그를 메모리 목록에 모으는 테스트용 어펜더.
- **고친 방법:** 세 로거에 `ListAppender`를 TRACE로 붙여 0건인지 센다. "전체 로그에 키 없음"은 콘솔 검사로 유지(누가 남겼든 없어야 하니까). 가짜 서버 로그는 끈다(약속에 없는 요청을 키째로 찍기 때문).
- **원칙:** 확인하려는 것에 **가장 가까운 곳**에서 확인한다.

### 6. 상속 관계 때문에 검사 순서가 중요하다 (재리뷰)

- **상황:** "연결 대기 시간 초과는 CONNECTION, TIMEOUT보다 먼저 검사"로 정했는데 이를 확인하는 테스트가 없었다.
- **개념:** `HttpConnectTimeoutException`은 `HttpTimeoutException`의 **자식**이다. 자식은 부모 검사(`instanceof`)에도 "맞다"고 나온다. 넓은 "시간 초과인가?"를 먼저 물으면 연결 문제가 TIMEOUT으로 들어간다. 비유: "서울"함을 먼저 보면 "강남구" 편지도 전부 "서울"함에 들어간다.
- **고친 방법:** 진짜 네트워크 없이 예외 객체만 만들어 분류 함수에 넣는 짝 단위 테스트: `HttpConnectTimeoutException` → CONNECTION, `HttpTimeoutException` → TIMEOUT.
- **원칙:** 재현이 어려운 상황은 통합 테스트를 포기하더라도 **판단하는 코드만 떼어 단위 테스트**로 지킨다.

### 7. 라이브러리가 일하는 순서가 우리 방어를 건너뛰었다 (PR 리뷰 지적 4)

- **상황:** `retrieve().onStatus(...).body(String.class)`로 "오류 상태면 우리 예외로 감싼다"를 만들고, 그 밖의 실패는 `catch (RestClientException e)`로 잡았다.
- **실제 (Spring 7.0.10 소스):** `body()`는 Content-Type 해석(221행)을 상태 처리(223행)보다 **먼저** 한다. 서버가 `Content-Type: not-a-type`을 보내면 상태 처리에 가기도 전에 `InvalidMediaTypeException`이 난다.
- **왜 catch를 빠져나갔나 (개념):** 이 예외는 `IllegalArgumentException`의 자식이고, `RestClientException` 집안이 아니다. catch는 **자기 집안 예외만** 잡는다. 게다가 메시지에 헤더 값 전체가 들어가므로, 헤더에 키가 되돌아오면 키째로 밖에 나간다.
- 비유: 경비실(상태 확인)을 지나야 건물에 들어가는 줄 알았는데, 택배 기사(Content-Type 해석)가 경비실 앞에서 먼저 상자를 뜯다가 사고가 난 경우.
- **고친 방법:** `exchange()`로 바꿔 상태부터 읽는다. 4xx/5xx는 Content-Type을 해석하지 않고 바이트로 읽는다. 200은 기존 변환기(`bodyTo`)를 쓰되, 지금은 `IllegalArgumentException` 전체를 우리 예외로 감싼다. 해석할 수 없는 Content-Type 예외(`InvalidMediaTypeException`)도 이 안에 들어간다. 범위를 좁힐지는 아래 "남은 것"에서 사람이 정한다.

  | 응답 | 전 | 후 |
  |---|---|---|
  | 401 + 잘못된 Content-Type (E14) | Spring 예외가 그대로 나감, 상태 없음 | `HTTP_ERROR status=401 ... code=-4` |
  | 200 + 잘못된 Content-Type (E16) | Spring 예외가 그대로 나감 | `IO status=200 ... cause=...InvalidMediaTypeException` |
  | 헤더 값에 키 (E17) | 메시지에 키 | 메시지·스택 트레이스 어디에도 키 없음 |

- **원칙:** "이 catch가 모든 실패를 잡는다"고 믿기 전에, 라이브러리가 **어떤 순서로** 무엇을 하고 **어떤 집안의 예외**를 던지는지 소스로 확인한다.

### 8. 이미 알게 된 정보는 다음 단계가 실패하기 전에 붙잡아 둔다 (PR 리뷰 지적 3)

- **상황:** 503 응답에서 본문을 읽다가 연결이 끊기면(E12), 본문 읽기 예외가 `RestClientException`으로 바뀌어 바깥 catch로 갔다. 이 catch는 상태를 모르니 `status` 칸이 비었다.
- **실제로 잃은 것:** "서버가 503이라고 답했다"는 사실. 재시도(#6)는 503(잠깐 고장)과 401(키 문제)을 다르게 다뤄야 하는데, 그 근거가 사라진다.
- **고친 방법:** 상태를 먼저 변수에 저장하고, 본문 읽기 실패는 그 자리에서 `ioErrorAfterStatus`로 감싼다 → `IO status=503 ...`. 잘린 JSON에서 code를 억지로 꺼내지는 않는다(E13).
- 비유: 전화가 끊기기 전에 상대 이름부터 받아 적기.
- **원칙:** 여러 단계로 처리할 때, 앞 단계에서 확인한 사실을 뒤 단계 실패가 지우지 않게 한다.

### 9. 문서가 규칙을 줄여 적으면 리뷰가 계속 붙잡는다 (후속 지적 2건)

- **상황:** 결정 문구에 "본문 읽기 실패는 IO"라고만 적었다. 실제 코드는 기존 분류 규칙(`kindOf`)을 따라 타임아웃이면 TIMEOUT, 연결 타임아웃이면 CONNECTION이 된다.
- **결과:** CodeRabbit이 "문서와 테스트(E20)가 다르다"고 한 번, 고친 문구에 "CONNECTION 예외가 빠졌다"고 또 한 번 지적했다.
- **고친 방법:** 결정 문구가 "기존 분류 규칙을 따른다"를 먼저 말하고, 예외를 빠짐없이 괄호로 적게 했다.
- **덤으로 알게 된 것:** 실제로 본문을 읽던 중 타임아웃이 나면 Spring은 본문 스트림을 닫는다(`JdkClientHttpRequest` 283~289행). 그 뒤 읽기가 일반 `IOException`을 던지면 실제 경로에서는 IO가 된다. 어떤 예외 타입이 나오는지는 이 코드가 정하지 않고, 실행해서 확인하지도 않았다. E20은 분류 규칙을 지키는지만 보는 **단위 가드**라서 실제 경로의 분류는 확인하지 않는다(실제 경로 통합 테스트는 "남은 것"에 보류).
- **원칙:** 규칙을 다른 곳에 다시 적을 때는 줄이지 말고, 원래 규칙을 가리키거나 예외까지 전부 적는다.

### 10. 리뷰 지적이라고 다 받아들이지는 않는다

- **지적:** "범위 밖 파일" 자동 검사가 3번 연속 "01 문서는 이 PR과 상관없으니 빼라"고 했다.
- **판단:** 채택 안 함. `dev`에는 TDD 기록 폴더가 아직 없어서, 빼면 PR #3의 기록이 어디에도 남지 않는다. PR 본문에 넣은 이유를 적었고, 병합을 막는 필수 검사도 아니다.
- **원칙:** 채택하지 않을 때는 이유를 코드·저장소 상태에서 확인해서 답글로 남긴다. 말없이 무시하지 않는다.
