# 02. 서비스 키 노출 방어 (이슈 #4, OPS-5)

- 기간: 2026-11-14 ~
- 브랜치: `fix/service-key-log-masking`
- 상태: **2단계(테스트 작성) — 리뷰 지적 반영 중**

## 목표

공공 API 호출이 실패했을 때, 오류 메시지·스택 트레이스·로그·운영 API 응답 어디에도 서비스 키가 나오지 않게 한다.

## 무엇이 진짜 문제였나

```
500 Internal Server Error: "<html><body>Internal Error ab+c/d==</body></html>"
```

`ab+c/d==`가 테스트용 가짜 키다. 공공 API 오류 페이지가 요청 주소를 그대로 되돌려 주면, 진짜 키가 이렇게 예외 메시지에 들어간다.
비유하면 **반송 봉투의 주소는 가렸는데, 상대가 편지 안에 내 비밀번호를 적어 돌려보낸 경우**다.

**배운 점:** 이슈의 전제는 소스와 실제 실행으로 확인한 뒤에 적는다. 이번에는 "URL로 샌다"는 전제는 틀렸지만, 테스트를 써 보니 "본문으로 샌다"는 진짜 경로가 나왔다.

## 케이스와 결정

| 결정 | 이유 |
|---|---|
| 실패는 우리 예외 `Gov24ApiException`으로 감싼다. 메시지는 종류·HTTP 상태·경로·page·공공 API `code`만 | 라이브러리가 바뀌어도 메시지 형식이 안전하게 유지되고, 재시도(#6)가 기댈 예외 종류가 생긴다 |
| 원래 예외는 안에 넣지 않고 클래스 이름만 | 넣으면 로그의 "Caused by" 줄에 원래 메시지와 본문이 그대로 나온다 |
| 응답 본문은 넣지 않고 공공 API `code`만 (예: `code=-4`) | 원인 파악에는 code로 충분하고, HTML 오류 페이지에는 무엇이 들어 있을지 모른다 |
| 외부에서 온 글은 키 네 형태를 `****`로 가린다 | 원래 값 `ab+c/d==`, 대문자 인코딩 `ab%2Bc%2Fd%3D%3D`, 소문자 인코딩, 부분 인코딩 `ab%2Bc/d==` |
| `Gov24Client`는 로그를 남기지 않는다 | 같은 실패가 여러 번 찍히지 않게. 로그는 실패를 처리하는 쪽이 남긴다 |
| HTTP/1.1 고정 | 아래 리뷰 1번 |
| 연결을 맺지 못함 = CONNECTION, 맺은 뒤 문제 = IO | 아래 리뷰 2번 |

## 리뷰에서 배운 것

### 1. 테스트가 시험하는 상황이 케이스와 달랐다 (E7)

- **상황:** "응답 본문이 중간에 깨지면 IO로 감싸는지" 시험하려고 가짜 서버에 깨진 본문을 보내게 했다.
- **실제:** `protocol error: Frame type(100) length(7107435) exceeds MAX_FRAME_SIZE(16384)` — 본문 잘림이 아니라 HTTP/2 형식 오류였다.
- **원인 (개념):**
  - 자바 HTTP 클라이언트의 기본값은 **HTTP/2**라서 `http://`에도 "HTTP/2로 바꿀까?"를 먼저 묻는다(업그레이드).
  - 가짜 서버가 받아들인 뒤 깨진 **글자**를 보내자, 클라이언트는 그걸 HTTP/2 **프레임 머리**(길이·종류가 적힌 앞부분)로 읽었다. 글자가 "길이" 자리에 들어가 700만이라는 값이 나왔다.
  - 비유: "이제 숫자로 대화하자"고 약속한 직후 상대가 영어 단어를 보낸 상황.
- **고친 방법:** 클라이언트를 HTTP/1.1로 고정하고, "본문 1,000바이트"라고 알린 뒤 10바이트만 보내고 끊어서 진짜 잘림을 재현한다.
- **원칙:** 테스트가 실패할 때 **실제 실패 메시지**를 읽고, 그게 케이스가 말하는 상황인지 확인한다.

### 2. 예외 종류로 나눌 수 없는 것을 종류로 나누려 했다 (E6)

- **상황:** "연결 실패"와 "연결 끊김"을 둘 다 CONNECTION으로 분류하기로 했었다.
- **원인 (개념):**

  | 경우 | 단계 | 자바가 주는 예외 |
  |---|---|---|
  | 포트 닫힘 | 연결을 맺기 **전** (TCP 핸드셰이크에서 거절) | 항상 `ConnectException` |
  | 연결 끊김 (reset) | 연결을 맺고 요청을 보낸 **뒤** | 일반 `IOException`, EOF 등 그때그때 다름 |

  - 비유: "없는 번호입니다"는 늘 같은 안내지만, 통화 중 끊김은 끊기는 순간마다 다르게 들린다.
  - WireMock의 연결 끊김 재현은 Windows에서 멈출 수 있다고 문서에 적혀 있다.
- **고친 방법:** 기준을 "연결을 맺었는가"로 바꿨다. 맺지 못함(포트 닫힘, 연결 대기 시간 초과) = CONNECTION, 맺은 뒤 문제 = IO. 연결 대기 시간 초과는 자바에서 "시간 초과" 예외의 한 종류라 TIMEOUT보다 **먼저** 검사한다.
- **잃는 것:** 없다. 재시도(#6)에서 둘 다 다시 시도할 대상이다.

### 3. 몸 풀기 첫 바퀴에도 기록 제한을 걸었다 (타임아웃)

- **상황:** 0.3초 타임아웃 클라이언트를 정상 응답 테스트에도 썼다.
- **실제:** 이 PC에서도 첫 호출이 0.46초 걸렸다(연결 준비, 클래스 로딩, JIT). GitHub의 CI 서버는 더 느릴 수 있다.
- **원칙:** 코드가 맞는데 통과했다 실패했다 하는 **흔들리는 테스트(flaky)**는 진짜 실패를 무시하게 만든다.
- **고친 방법:** 정상 테스트는 5초, 짧은 제한은 타임아웃 시험에만. 지연은 제한의 몇 배로.

### 4. 설정을 무시한 구현도 통과했다 (E5)

- **상황:** 지연 3초, 설정 0.3초로 "TIMEOUT이 나는지"만 봤다. 설정을 무시하고 1초를 박아 넣어도 3초 전에 끊기니 통과한다.
- **리뷰 제안의 한계:** "2초 안에 끝났나"를 더해도, 1초 고정 구현은 2초 안에 끝나서 여전히 통과한다.
- **고친 방법 (짝 테스트):** 같은 지연(1.5초)에 설정만 바꿔 두 번.

  | 엉터리 구현 | 짧은 설정(0.3초) → TIMEOUT 기대 | 긴 설정(5초) → 정상 기대 |
  |---|---|---|
  | 1초 고정 | 통과 | **실패** |
  | 10초 고정 | **실패** | 통과 |
  | 타임아웃 없음 | **실패** | 통과 |
  | 설정대로 | 통과 | 통과 |

- **원칙:** "A면 B"를 하나만 보면 B가 다른 이유로 일어나도 통과한다. **조건을 바꾸면 결과도 바뀌는지** 짝으로 본다.
- connect-timeout은 "응답 없는 IP" 재현이 네트워크마다 달라서 이번에는 시험하지 않는다(범위 밖에 기록).

### 5. 로그를 콘솔 글자 모양으로 확인했다 (E11)

- **상황:** "Gov24Client는 로그를 남기지 않음"을 콘솔에서 `Gov24Client  :` 글자를 찾아 확인했다.
- **놓치는 경우:** 로그 형식이 JSON으로 바뀜 / 다른 로거 이름 / DEBUG 로그(기본 INFO라 콘솔에 안 나옴. 운영에서 DEBUG를 켜면 그때 샌다).
- **개념:** 로거(로그 창구), 레벨(TRACE < DEBUG < INFO < WARN < ERROR), 어펜더(로그를 보낼 곳). `ListAppender`는 로그를 메모리 목록에 모으는 테스트용 어펜더.
- **고친 방법:** 세 로거에 `ListAppender`를 TRACE로 붙여 0건인지 센다. "전체 로그에 키 없음"은 콘솔 검사로 유지(누가 남겼든 없어야 하니까). 가짜 서버 로그는 끈다(약속에 없는 요청을 키째로 찍기 때문).
- **원칙:** 확인하려는 것에 **가장 가까운 곳**에서 확인한다.
