## 리뷰에서 배운 것

### 1. 리뷰어 봇도 검증 대상이다
"늘 PASS"는 안심 신호가 아니라 경고 신호다. 같은 커밋을 다른 리뷰어(CodeRabbit)가 본 결과와 비교해서 구멍을 찾았다.

### 2. 판정 스크립트는 검사받는 쪽이 고칠 수 없는 곳에서 실행한다 (S1)
검사 스크립트를 PR 쪽에서 돌리면 PR이 그 스크립트를 고쳐 자기 자신을 통과시킨다. 시험에 답안지와 채점기를 같이 내게 하는 꼴이다. 기준 브랜치 원본을 꺼내 돌린다.

### 3. 형식 검사는 앞부분이 아니라 전체 모양을 본다 (B4·B13)
"확인함으로 시작하면 통과"는 `확인함(문제 있음)`도, 지침의 형식 줄을 그대로 복사한 `확인함 | 해당 없음 | 문제 | …`도 통과시켰다. 상태 → 긴 대시 → 근거까지 정확한 모양을 요구한다.

### 4. 외부 글을 로그 메시지에 그대로 붙이지 않는다 (S3)
옛 인라인 코드는 리뷰 본문 줄을 `::error::` 메시지에 붙였다. 본문에 `\r` 뒤 `::add-mask::`를 숨기면 GitHub가 그것을 명령으로 읽을 수 있었다. 메시지에는 항목 이름만 넣는다.

### 5. 기본값을 믿지 말고 실행 로그로 확인한다 (pipefail)
`shell`을 지정하지 않으면 GitHub는 `bash -e`만 쓰고 `pipefail`은 켜지 않는다. 로그의 `shell:` 줄로 확인했다.

### 6. 리뷰 워크플로 변경이나 기준 브랜치의 스크립트 부재로 판정에 실패할 수 있다
리뷰 워크플로 파일이 dev와 다르면 Claude가 실행을 건너뛴다. 그러면 이 커밋에 이미 낸 Claude 판정도 없을 때 판정 확인 단계는 "판정 없음"으로 실패한다(같은 커밋을 다시 돌리는 경우처럼 앞서 낸 판정이 있으면 그 판정으로 결정된다). 워크플로가 꺼내는 판정 스크립트(`check-claude-verdict.sh`, `select-claude-review.jq`, `fetch-claude-verdict.sh`)가 기준 브랜치에 없으면 "스크립트가 없어 판정할 수 없습니다"로 실패한다. 둘 다 안전한 쪽 실패지만, 병합하려면 관리자 우회가 필요하다. 규칙의 우회 목록이 비어 있으면 관리자도 못 한다. 판정 확인 단계 자체를 지우거나 바꾸는 PR은 이 범위에 들지 않는다. 그런 PR은 이 작업 시점에는 통과할 수 있었다(아래 "후속"에서 2026-11-18에 승인 필수로 대부분 막음(#16~#19에서 시험함). CODEOWNERS 잠금(W29)은 병합 뒤 시험 전이고, W20 경쟁은 다음 별도 PR. W20의 B 커밋도 `.github/`를 고치므로 잠금에 걸릴 것으로 보지만 짐작이며 시험 전).
