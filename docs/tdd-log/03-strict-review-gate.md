## 결론 (한 줄)

**Claude 리뷰는 "거의 무조건 PASS"에서 "점검표와 근거가 없으면 통과 못 함"으로 바뀌었고, PR이 판정 스크립트를 고쳐 스스로 통과하는 길도 막혔다.** 실제 시험 PR에서 막을 것은 막고(#12), 정상 PR은 통과시켰다(#13 첫 커밋 `7ef981f`). 단, **PR이 워크플로 파일 자체를 고치는 우회는 아직 막지 못한다**(아래 "남은 것").

## 왜 시작했나

PR #8에서 7번, PR #10에서 2번, 모두 9번 Claude 리뷰는 전부 PASS였다(각 PR의 `claude[bot]` APPROVED 수). 같은 기간에 CodeRabbit은 실제로 맞아서 반영한 지적을 8건 냈다(PR #8: 처음 4건과 후속 문구 2건, PR #10: 2건. 채택하지 않은 "범위 밖 파일" 검사는 뺌). 리뷰 본문에는 "PR 기재 Green 93/93을 신뢰"라고 적혀 있었다. 직접 확인하지 않고 PR 본문을 믿었다는 뜻이다.
비유하면 **학생이 낸 자기 채점표를 보고 도장만 찍는 감독관**이었다.

## 지금 판정은 이렇게 돈다

1. Claude가 리뷰하고 Approve 또는 Request changes를 낸다. 본문에 점검표 6줄을 쓴다.
2. 판정 확인 단계가 **PR의 기준 브랜치(`origin/$BASE_REF`, 지금 작업 PR은 dev)에 있는** `fetch-claude-verdict.sh`, `select-claude-review.jq`, `check-claude-verdict.sh`를 꺼내 실행한다(`git show "origin/$BASE_REF:…"`). 없으면 실패. 워크플로 트리거는 대상 브랜치를 제한하지 않으므로, main 대상 PR은 main의 스크립트로 판정한다.
3. 리뷰 목록 전체(여러 페이지)에서 `claude[bot]`이 이 커밋에 낸 마지막 판정을 고른다.
4. Approve여도 점검표가 형식에 맞아야 통과: 항목마다 정확히 한 줄, `<줄 머리> <상태> — <근거>`, 상태는 `확인함`·`확인함(문제 없음)`·`해당 없음`, 첫 줄은 `PASS:`.

## 리뷰에서 배운 것

### 1. 리뷰어 봇도 검증 대상이다
"늘 PASS"는 안심 신호가 아니라 경고 신호다. 같은 커밋을 다른 리뷰어(CodeRabbit)가 본 결과와 비교해서 구멍을 찾았다.

### 2. 판정 스크립트는 검사받는 쪽이 고칠 수 없는 곳에서 실행한다 (S1)
검사 스크립트를 PR 쪽에서 돌리면 PR이 그 스크립트를 고쳐 자기 자신을 통과시킨다. 시험에 답안지와 채점기를 같이 내게 하는 꼴이다. 기준 브랜치 원본을 꺼내 돌린다.

### 3. 형식 검사는 앞부분이 아니라 전체 모양을 본다 (B4·B13)
"확인함으로 시작하면 통과"는 `확인함(문제 있음)`도, 지침의 형식 줄을 그대로 복사한 `확인함 | 해당 없음 | 문제 | …`도 통과시켰다. 상태 → 긴 대시 → 근거까지 정확한 모양을 요구한다.

### 4. 외부 글을 로그 메시지에 그대로 붙이지 않는다 (S3)
옛 인라인 코드는 리뷰 본문 줄을 `::error::` 메시지에 붙였다. 본문에 `\r` 뒤 `::add-mask::`를 숨기면 GitHub가 그것을 명령으로 읽을 수 있었다. 메시지에는 항목 이름만 넣는다.

### 5. 기본값을 믿지 말고 실행 로그로 확인한다 (pipefail)
`shell`을 지정하지 않으면 GitHub는 `bash -e`만 쓰고 `pipefail`은 켜지 않는다. 로그의 `shell:` 줄로 확인했다.

### 6. 판정 확인 단계를 그대로 둔 채 리뷰 워크플로를 고치는 PR, 또는 기준 브랜치에 아직 없는 판정 스크립트에 기대는 PR은 판정받지 못한다
리뷰 워크플로 파일이 dev와 다르면 Claude가 실행을 건너뛴다. 그러면 판정 확인 단계는 "판정 없음"으로 실패한다. 워크플로가 꺼내는 판정 스크립트(`check-claude-verdict.sh`, `select-claude-review.jq`, `fetch-claude-verdict.sh`)가 기준 브랜치에 없으면 "스크립트가 없어 판정할 수 없습니다"로 실패한다. 둘 다 안전한 쪽 실패지만, 병합하려면 관리자 우회가 필요하다. 규칙의 우회 목록이 비어 있으면 관리자도 못 한다. 판정 확인 단계 자체를 지우거나 바꾸는 PR은 이 범위에 들지 않는다. 그런 PR은 통과할 수 있다(아래 "남은 것").
